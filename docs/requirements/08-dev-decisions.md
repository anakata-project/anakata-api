# 08 · Development decisions
Decisions taken by the development team at the start of the build. They sit **above** documents 01–07 and the prototypes in the order of authority, because they resolve contradictions between them. Items marked **PENDING CLIENT** are our working assumption until Anakata confirms; they are implemented as configurable values so changing them later is data, not code.

---

## A · Architecture

| # | Decision |
|---|---|
| A1 | **Four repositories**: `anakata-api`, `anakata-ui`, `anakata-panel`, `anakata-engine`. |
| A2 | **One tightly coupled Laravel application** (`anakata-api`). RMS and CRM are two sections of one codebase and one database (A3), not separate modules. Conventional folders: `app/Models`, `app/Actions/<Domain>`, `app/Services/<Domain>`, `app/Enums`, `app/Policies`, `app/Events`, `app/Listeners`, `app/Http/{Controllers,Requests,Resources}/{Rms,Crm,Engine}`, `app/Support`. No `app/Modules`, no contracts between RMS and CRM, no mirrors, no internal sync events. Route prefixes `/api/rms`, `/api/crm`, `/api/engine` exist for permissions (`panel.rms` / `panel.crm`), the public/private split, and the CRM sensitive-data guard. A Pest arch test keeps CRM controllers off money/booking write paths (see `laravel.mdc`). Foreign keys between RMS and CRM tables are allowed. |
| A3 | **One MySQL 8 database** — `anakata` (app) and `anakata_test` (tests) — with a single MySQL user that has grants on both. RMS and CRM are two sections of one codebase sharing this one database; foreign keys between their tables are allowed (e.g. a booking references a CRM contact; a CRM contact converts into an RMS customer). Sensitive data (passport number, medical/dietary/accessibility notes) is protected in code — encrypted at rest with a dedicated key (`SENSITIVE_DATA_KEY`, separate from `APP_KEY`) — and by a CRM response-guard middleware, not by DB-role isolation. |
| A4 | **Events are side effects only.** Laravel events + queued listeners (Redis, Horizon), dispatched after commit (`ShouldDispatchAfterCommit`): emails, Stripe, engine availability push, CRM tasks raised by booking changes. No outbox, no `EventEnvelope`, no internal sync bus. CRM data derived from bookings (pipeline stages 5–7, lifecycle, LTV) is computed from the booking tables directly. External integrations (Stripe, email, the public engine) still follow doc 07's intent. |
| A5 | **Auth**: Laravel Sanctum SPA cookie sessions for RMS and CRM staff (same user table, on the single default connection). **Permissions are a PHP enum (code); roles are a `roles` table (data)** holding a JSON list of enum values, managed by Admins in the RMS; one role per user. No permissions package or permissions table. The finance and director flags are permissions in the enum. The public engine is unauthenticated and rate-limited. The agent portal (later) gets its own guard. |
| A6 | **Frontends**: Nuxt 4 + Nuxt UI v4 + TypeScript. **One staff panel (`anakata-panel`, SPA) contains both the RMS and the CRM**; the engine is SSR for SEO. Both extend the `anakata-ui` layer via the local path `../anakata-ui` for now (A13). |
| A7 | **API contract**: OpenAPI generated by Scramble; the layer generates TypeScript types from it. The API is deployed before the frontends that depend on a change. |
| A8 | **Documents / PDF**: rendered from HTML templates with headless Chromium (Browsershot or Gotenberg — chosen in the documents sprint), because the invoice must reproduce mockup v6 exactly. |
| A9 | **Integrations** behind interfaces with fakes for development and tests: Stripe (payments, test mode), Microsoft Graph for Exchange (email; Mailpit locally). |
| A10 | **Local ports**: engine 3000 · panel 3001 · API 8000 (· ui playground 3010). |
| A11 | **The panel.** RMS and CRM live in one Nuxt app (one codebase) with a **section switch in the header** (RMS ⇄ CRM) that swaps the sidebar navigation. The current section is derived from the URL (`/rms/…`, `/crm/…`), so deep links and browser history work; switching goes to the last page visited in the other section. Pages live in `app/pages/rms` and `app/pages/crm`; components are organised by feature; one `useApi()`. No local Nuxt layers, no import ban, no `useRmsApi` / `useCrmApi`. Cross-section links (deal → booking) are route links only. Access to each section is a permission (`panel.rms`, `panel.crm`, Sprint 1); a user with only one sees no switch. The API still enforces that the CRM has no write path to money. |
| A12 | **Laravel 13** (PHP ≥ 8.3). |
| A13 | **No CI for now.** Git host is undecided (likely not GitHub). Local quality checks remain mandatory. Apps consume `anakata-ui` via the local path `../anakata-ui` until remote consumption is decided with the git host. |

## D · Sprint 1 decisions (18 Sep 2026)

| # | Decision |
|---|---|
| D1 | **Sign-in**: email and password, plus "forgot password". No two-factor authentication yet (to be revisited before go-live; Sanctum sessions leave room for it). |
| D2 | **Users**: no self-registration. An admin creates a user, who receives an invitation email with a link, valid 7 days, to set a password. The first admin in each environment is created with `php artisan anakata:create-admin`. Users are never deleted, only disabled. |
| D3 | **Roles**: three seeded system roles, Admin, Manager and Sales Exec. System roles cannot be deleted or renamed. **Admin always holds every permission** (including permissions added later) and cannot be edited. Manager and Sales Exec permissions can be edited. Admins can add roles. One role per user: a user who needs a flag their role lacks (the prototype's "CFO (external) · Agent + finance") gets a role that includes it. |
| D4 | **Permissions per area** (`bookings.*`, `requests.*`, `offers.*`…). Refunds are split into `refunds.approve` (director group) and `refunds.execute` (finance group). The own-records rule lives in policies, not in the enum. The one related permission is `records.act_on_any`, which lets a role bypass the rule (Admin by default). |
| D5 | **One append-only `change_history` table** for every entity: when, who, event, before/after, reason where required. Rows are never updated or deleted (enforced in code and by database triggers). **Sensitive values are never written to history**, only the field name. Rates, business rules and engine settings additionally keep their own publish history (doc 02). |
| D1a | **Password length** (19 Sep 2026): minimum **8** characters, no composition rules; `uncompromised()` (breached-password check) in production only. Replaces the 12 characters specified in Sprint 1 task 03. |
| D6 | **Time**: everything is stored and exchanged in UTC (ISO-8601 with `Z`). The panel shows timestamps in Galápagos time (`Pacific/Galapagos`, UTC−6, no daylight saving). Calendar dates (departure dates, date of birth) are dates and are never shifted. The business time zone also decides the year in references (`ANK-2026-…`) and, later, business-hour calculations. |

## E · Sprint 2 decisions (19 Sep 2026)

| # | Decision |
|---|---|
| E1 | **Configuration is versioned documents.** Rates, business rules and engine settings are each an append-only series of published versions, one table per kind (`rate_versions`, `business_rule_versions`, `engine_settings_versions`). A version holds the whole document as JSON, validated by a typed PHP class, and is never changed after it is written. The current value is the highest version. |
| E2 | **No stored drafts.** The draft lives in the editor, as in the prototype. Publishing sends the whole document plus the version the edit started from (`base_version`). If someone else published in between, the API answers 409 and nothing is overwritten. The API can validate a draft and run the price check without storing anything. |
| E3 | **Approval reference**: a mandatory text field for every rates and business-rules publish, and for engine-settings publishes that change a rule field. Copy-only engine-settings changes may leave it empty. No second-person approval step. |
| E4 | **Publishing applies immediately.** No "effective from" date: rates are already chosen by the departure's sailing year, and confirmed bookings keep their contracted price. |
| E5 | **The business-rules registry is code, the values are data** (the same split as permissions and roles). The registry lists every rule with its source code, status, source value and where it is set. The API computes the "differs from source" flag. |
| E6 | **Engine settings have two edit levels**, as in the prototype. Rule fields (guests, calendar, fees, charter response SLA) need `engine_settings.manage` (Admin by default). Copy fields need the new permission `engine_copy.manage` (Admin and Manager by default). |
| E7 | **The core pricing calculation lives in the API** as a pure service (doc 02 steps 1–7). The eight reference prices in doc 02 are its tests. Offers, promo codes and the online-deposit discount are added with the engine API (08 B2). Bookings will store the id of the rates version they were priced with (Sprint 4). |
| E8 | **Items pending with the client are built with their documented defaults and marked pending** in the registry: `online_deposit_discount_pct` 5 and `max_total_discount_pct` none (08 B2, PENDING CLIENT), and the cancellation bands, whose logic is live while the customer-facing text is still being written (LEG-001). |
## F · Sprint 3 decisions (20 Sep 2026)

| # | Decision |
|---|---|
| F1 | **One `cabin_claims` table is the only source of occupancy.** Everything that takes a cabin on a departure writes one claim row per cabin: an internal block now; a booking, a request or a web checkout later. A unique index on the *active* (departure, cabin) pair, via a generated column that is NULL once the claim is released, makes the database refuse a second active claim. Availability, the calendar, the yacht layout and the engine feed are computed from claims; availability is never typed. |
| F2 | **One booking occupies one cabin; a charter occupies all nine** (nine claims under one booking). Several cabins booked together are separate bookings linked by a group. Recorded now because the claim model depends on it; bookings arrive in Sprint 4. |
| F3 | **A hold is a claim with an expiry**, owned by whatever placed it (a request or agency booking in Sprint 4, a web checkout in the engine sprint). There is no separate hold table. Expired holds are released by a job every minute, and immediately when a new claim collides with an expired one. |
| F4 | **Yachts and cabins are fixed reference data**, seeded in every environment and not editable in the RMS: ANAMARA and ANATIVA, each with cabins S1–S8 (Suite 01–08) and OWNER (Owner's Suite). |
| F5 | **Calendar dates are dates.** Departure dates are `DATE` columns, exchanged as `YYYY-MM-DD` through a dedicated cast, and never pass through the UTC timestamp serializer (D6). "Sunday" is checked on the date itself. |
| F6 | **Demo inventory is local only.** The three itineraries, sixteen departures and a sample block from the prototype seed data are seeded only in `local` and `testing`. Production itineraries and departures are entered in the RMS (the 2027 calendar is still pending, PRO-001). |
| F7 | **Festive is stored per departure.** "Generate season" marks departures from 15 Dec to 2 Jan as festive and gives them the festive itinerary. Editing one yacht's departure warns when the other yacht's departure on the same date has a different festive flag. |
| F8 | **Holds & Waitlist move to Sprint 4**, with bookings and requests, which are what create holds (`WAITLISTED` and `ON_HOLD_AGENCY` are booking states in doc 02). Sprint 3 builds the hold mechanism (claims with expiry and the release job) without a screen. |
| F9 | **"Limited availability"**: when no cabin on a departure is free but at least one is only held, the engine label is `LIMITED AVAILABILITY` (doc 04 §4.4), not `FULL`. |
## G · Sprint 4 decisions (20 Sep 2026)

| # | Decision |
|---|---|
| G1 | **Contacts start small.** A booking's client of record is a `contacts` row: name, email, phone, country, preferred channel. When an email is given, the contact is found or created by the normalised email; without one, a new contact is created. The CRM (Sprint 9) extends this table with identity resolution, aliases and merging. It doesn't replace it. |
| G2 | **Reservations.** One booking = one cabin (F2). A charter is one booking with nine claims and no cabin. A manual reservation for several cabins creates one booking per cabin under a group (GRP-NNN), which is created on the spot or chosen from the departure's existing groups. The first booking's client becomes the group coordinator. |
| G3 | **References.** A manual reservation gets `ANK-YYYY-NNNN` when it is created. A web request is created as `ANK-R-YYYY-NNNN` and receives its `ANK-YYYY-NNNN` when it reaches CONFIRMED (prototype `confirmReq`: "booking ID assigned" on payment). The request reference is kept on the booking for traceability. This answers the Sprint 1 question. |
| G4 | **Contracted price.** A booking stores the rates version it was priced with, the price lines, the total, the deposit % and the balance days at creation, and later rate publishes never change them. **A date change reprices** (prototype Overview: "availability check → automatic re-price (rate year / festive flag may change) → confirm delta"): the move is quoted at the current rates for the new departure, staff see the difference and confirm it, and the booking takes the new rates version, lines and total. The deposit % and balance days stay as sold. There is no modification fee (FIN-006). |
| G5 | **Business hours for holds (TEC-004), pending the client's answer.** Business hours are Monday to Friday, 09:00 to 18:00 Galápagos time, with a list of holiday dates (empty by default). A request on a departure within 120 days is near-term (48 business hours); further out it is long-lead (5 business days). All of these are business-rule values marked PENDING CLIENT, added through the Sprint 2 shape-change procedure. |
| G6 | **What waits for Sprint 5 (payments):** automatic CONFIRMED / FULLY_PAID from payments, balances (until then a booking's balance equals its total), the OVERDUE flag and the OPS-007 decision, agencies, commissions and the `ON_HOLD_AGENCY` state, and cancellation penalties and refunds. In Sprint 4 these transitions are manual, with a reason where doc 02 requires one. |
| G7 | **The waitlist is its own table** (contact, departure, cabin category, notes), ordered first-in-first-out by creation, not a booking state. `WAITLISTED` stays in the status enum unused. "Notify now" is manual; automatic notification stays in the backlog (doc 06 item 4). |
| G8 | **Deletion is soft and audited.** Deleting a booking needs `bookings.delete` (Admin by default) and a reason; the row is soft-deleted, its claims released, and a history entry written. The "Deleted & released" list is built from history (`booking.deleted`, `booking.released`). |
| G9 | **Claims follow the status.** REQUESTED holds its cabin with a `HOLD` claim (type `REQUEST`, expiry from G5). PENDING_PAYMENT and later statuses hold a `BOOKING` claim. RELEASED, CANCELLED and CANCELLED_POSTPAID release the claims. **An expired request hold frees the cabin but never cancels the request** (prototype Booking Requests notice: "No request is ever auto-cancelled without team review; expiries release the hold and notify the owner"). The request stays REQUESTED, marked hold-expired, for staff to confirm (which re-claims the cabin if it is still free) or release. |
| G10 | **The departure row is the lock.** `ClaimService::claim` and `UpdateDeparture` both lock the departure's own row (primary key, `FOR UPDATE`) before anything else, so the date/yacht lock and new claims can never interleave (Sprint 3 review). |
## H · Sprint 5 decisions (Sprint 5 planning)

| # | Decision |
|---|---|
| H1 | **The payments ledger is append-only.** Every payment is a row in one `payments` table: booking, kind (deposit, balance, extras, refund, other), method, amount in integer USD (negative for a refund), reference, gateway id, status, value date, who recorded it. Rows are never edited or deleted — a correction is a new row, and a refund is a negative row. A database trigger refuses `DELETE` and refuses `UPDATE` of `booking_id`, `kind`, `amount` and `reference`; `status` and `gateway_id` stay updatable, because a wire is marked received and a refund is executed. This is the same discipline as `change_history`. |
| H2 | **Balance comes from the ledger.** `Booking::balance()` becomes `total − settled payments`, and that is the single place G6 promised would change. `paid` is the sum of settled rows; the frozen `deposit_pct` still decides the deposit amount (G4), because the deposit is a share of the cabin charges, not a payment fact. |
| H3 | **Payment references** are `{booking display reference}-{letter}{NN}`: `D` deposit, `B` balance, `E` extras, `R` refund, `O` other, with a two-digit sequence per booking and kind (prototype `addPay`). They are drawn in `ReferenceService` with a single statement, like every other reference, under the booking row lock. |
| H4 | **Money moves the status, through the same table.** A settled deposit takes a PENDING_PAYMENT booking to CONFIRMED; a balance reaching zero takes it to FULLY_PAID. Both run through `TransitionBooking` with actor System and the payment reference as the reason, so the legal table, the history and the claims rules stay in one place. One class, `ApplyPaymentEffects`, decides this and is idempotent; nothing else infers status from money. The manual FULLY_PAID path stays, still needs a reason, and still says "(marked manually — … not in the payments record)" when the ledger disagrees. |
| H5 | **OVERDUE is a derived flag, not a status.** It is computed from the balance, the due date and the Galápagos calendar date, exactly as the prototype treats it ("OVERDUE is a flag over CONFIRMED"). `BookingStatus::Overdue` stays in the enum unused, like `WAITLISTED`, so claims keep following the status (G9). The only persisted trace is one history entry the first time a booking crosses, for the team and for later alerts. The OPS-007 decision — extend with a new due date, or cancel per policy — is always a human action with a mandatory reason. **No automation ever cancels a booking.** |
| H6 | **A wire is pledged, not paid.** A wire payment is recorded as `AWAITING_WIRE`: it shows on the booking with its window (`payments.wire_window_hours`) but never counts towards `paid` and never moves the status. Finance marks it received with the bank reference (`payments.mark_wire_received`), and only then does it settle and take effect. The window alerts; it does not release anything. |
| H7 | **Stripe is the source of settlement (TEC-001).** The RMS creates payment links; Stripe's webhook is what turns one into a settled payment. Anakata stores no card data — Stripe ids only. The webhook route sits outside the panel API with no session, verifies the signature, stores the event under a unique `stripe_event_id`, answers 200 and does its work in a queued job. It is idempotent twice over: once on the event id, once on the gateway id already present on a payment row. Amounts convert to cents only at the gateway boundary; inside the app money stays integer USD. |
| H8 | **Commission is frozen on the booking.** A trade booking stores its agency and commission percentage at sale, and later changes to the agency's rate never touch it. Above `commission.cap_pct` (12, FIN-005) the booking is created at `ON_HOLD_AGENCY`: it holds its cabin like any sold booking, but it cannot reach CONFIRMED — even when the deposit settles — until someone with `commissions.override_cap` approves it with a reason. Commission accrues on the booking and becomes payable `commission.payable_days_after_cruise` (30) days after the cruise; paying it out is a later sprint. |
| H9 | **Penalties and refunds.** Cancelling a booking with settled money computes the penalty band from `cancellation.bands` by Galápagos days before departure, and creates a refund request that freezes the band, the penalty (on the booking total) and the refund due (`paid − penalty`, never below zero). A later change to the bands never touches a queued request. Approval (`refunds.approve`) authorises; execution (`refunds.execute`) writes the negative payment to the ledger. The SLA is `sla.refund_business_days` (15) business days. Customer-facing cancellation wording stays unpublished until LEG-001. |
| H10 | **The lock order with payments.** Any writer that touches money follows the Sprint 4 order and extends it: departure row(s) → booking row → payment or refund row → reference counters. A payment carries a `booking_id` foreign key, so the booking must be locked before the insert, or the parent's shared lock upgrades and deadlocks. Webhooks and reconciliation take the same path as manual recording; there is no second way in. |
## I · Sprint 6 decisions (Sprint 6 planning)

| # | Decision |
|---|---|
| I1 | **Sensitive data has its own key.** Passport numbers and medical, dietary and accessibility notes are encrypted at rest by a dedicated cast using `SENSITIVE_DATA_KEY`, never `APP_KEY` and never a fallback to it, so rotating or leaking the application key does not expose them (B8). Encrypted columns cannot be searched or indexed; nothing needs to. These values never appear in history (redacted by field name), in logs, or in a CRM-section response (the guard). Key rotation — previous keys and a re-encrypt command — is a later sprint. |
| I2 | **The API masks; the panel never sees what it may not show.** Without `guests.view_sensitive`, the passport number is sent as `•••• ` plus its last three characters (prototype `mask`) and notes are sent as absent with an "on file" flag. The panel renders what it receives and never masks in the browser. A user who cannot read a passport number can still replace it: an empty value means unchanged, a typed value replaces. |
| I3 | **One guest record per passenger.** Guests belong to a booking, up to `guests.max_per_cabin` (cabin) or `guests.max_per_yacht` (charter), with exactly one lead. The priced party (`adults`, `children`) stays what was sold (G4); guests are the people, and a mismatch is an issue, not an automatic reprice. Date of birth and nationality are stored in clear text — the PNG category and the nationality aggregate need them — but stay in `SensitiveFields`, so history redacts them and no CRM response carries them. |
| I4 | **The PNG category and fee are derived and stored per guest.** The category follows FIN-004 and B6: exempt under `fees.png.exempt_under_age`; Ecuadorian nationals and residents at the national rate at any age; Andean Community members (CO, PE, BO) and all other foreigners split at 12 years old on the Galápagos departure date. Amounts come from the engine settings. The category and fee are stored on the guest and recomputed when the guest changes, when the booking moves, and when collection is switched on; a later publish of the amounts does not rewrite them (G4), which also lets the balance be summed in SQL. |
| I5 | **Minors, and validation that warns rather than blocks.** A guest who is under 18 today needs a guardian's name, relationship and a consent timestamp (§6.4, prototype `isMinorNow`). Being under the minimum age at departure (OPS-004), a passport expiring before the return date, a missing insurance declaration on a confirmed booking (OPS-005), children priced versus children present, and missing consents are issues the API computes and lists. None blocks saving: guest data arrives piece by piece. Whether a status transition should require complete guests is an open question. |
| I6 | **The consent log is append-only.** One row per document and version per booking — Terms & Conditions, cancellation policy, privacy policy and the travel-insurance declaration (required) and marketing (optional) — with the version, the time, the IP where there is one, and the source (engine, payment link or staff). A database trigger refuses updates and deletes; a withdrawal is a new row. Version labels are business-rule values, PENDING CLIENT (LEG-001, LEG-002). Staff-recorded consents record how they were obtained. Nothing is pre-checked, and consents are kept seven years and are outside the retention job. |
| I7 | **Retention jobs (B4).** A daily command anonymises passport number and expiry `retention.passport_months_after_cruise` months after the return date, and purges medical, dietary and accessibility notes `retention.medical_days_after_cruise` days after it, on Galápagos calendar dates, including soft-deleted bookings. It records counts, never values, as System, and has a dry run. The periods are PENDING CLIENT (LEG-002) and must be confirmed before the job runs in production. |
| I8 | **The extras catalogue is a versioned document; booking extras are frozen.** The catalogue is a fourth configuration document (`ConfigKind::Extras`), published with a base version and an approval reference by `extras.manage`, read only through `CurrentConfig`. Items are never renamed or removed once published — a retired item is inactive — because bookings reference their code. A booking extra snapshots the name, unit and rate at sale; a later publish never changes it (G4). Items priced "on request" take the rate staff enter. |
| I9 | **Charges, balance, and what OVERDUE means now.** `total` stays the cruise charges (G4). The charges total is cruise + extras + Galápagos fees Anakata collects, and `balance()` is the charges total minus what has been paid — changed in one place again, with its SQL twin. The deposit is still a share of the cruise charges only. Payments count against the cruise charges first: OVERDUE (H5) now means the cruise balance past its due date, so an unpaid extra never makes a booking overdue at T−120. Extras and collected fees are due `payments.extras_due_hours` before departure (shown, not flagged, until Sprint 11). FULLY_PAID still follows a zero balance; a charge added afterwards re-opens the balance but never moves the status back. Cancellation penalties stay on the cruise charges. |
| I10 | **Fee collection is a per-booking choice, and the lock order.** Each booking records whether Anakata collects the PNG fee and manages the TCT card; collected fees are charges, uncollected ones are information only. The default for new bookings is not collected until the client answers. Every write that can change a booking's balance — guests, extras, fee choices — takes the booking lock first, in the H10 order: departure → booking → child rows → reference counters. |

| J1 | **Templates are code; the browser prints previews; a PHP library makes the server PDFs. A correction is a new version with a mandatory reason, and every version stays downloadable. Viewing or printing an issued version renders it from its stored snapshot, so it shows what was issued then. Previews of documents not yet issued are rendered on demand and never stored. Documents are financial records, kept seven years and outside the guest-data retention job; they carry passenger names, never passport numbers, dates of birth or notes. |
