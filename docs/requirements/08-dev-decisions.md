# 08 · Development decisions
Decisions taken by the development team at the start of the build. They sit **above** documents 01–07 and the prototypes in the order of authority, because they resolve contradictions between them. Items marked **PENDING CLIENT** are our working assumption until Anakata confirms; they are implemented as configurable values so changing them later is data, not code.

---

## A · Architecture

| # | Decision |
|---|---|
| A1 | **Four repositories**, each with its own CI and deployment: `anakata-api`, `anakata-ui`, `anakata-panel`, `anakata-engine`. |
| A2 | **One Laravel application** (`anakata-api`) organised as a modular monolith: `Rms`, `Crm`, `Engine`, `Shared`. Module boundaries enforced by architecture tests. The RMS and CRM talk only through events (doc 07 §4) — so the CRM can be split into its own service later without redesign. |
| A3 | **Two MySQL 8 databases** — `anakata_rms` and `anakata_crm` — each with its own MySQL user. The CRM user has no grants on the RMS database, so passport and medical data are unreachable from CRM code at the database-role level (doc 07 §10.5). Known limit: both credentials live in one process, so this guards against code mistakes, not against a compromised server; full isolation comes if the CRM is ever deployed separately. |
| A4 | **Event transport**: transactional outbox table + Laravel queue (Redis, Horizon). At-least-once delivery, dedupe on `event_id`, 3 retries with exponential back-off, then a `[SYNC]` alert. Inside the monolith the "webhook" is a queued listener; the envelope is the same as doc 07 specifies so an HTTP transport can replace it later. |
| A5 | **Auth**: Laravel Sanctum SPA cookie sessions for RMS and CRM staff (same user table, on the `rms` connection). **Permissions are a PHP enum (code); roles are a `roles` table (data)** holding a JSON list of enum values, managed by Admins in the RMS; one role per user. No permissions package or permissions table. The finance and director flags are permissions in the enum. The public engine is unauthenticated and rate-limited. The agent portal (later) gets its own guard. |
| A6 | **Frontends**: Nuxt 4 + Nuxt UI v4 + TypeScript. **One staff panel (`anakata-panel`, SPA) contains both the RMS and the CRM**; the engine is SSR for SEO. Both extend the `anakata-ui` layer (pinned git tag in CI, local path in development). |
| A7 | **API contract**: OpenAPI generated by Scramble; the layer generates TypeScript types from it. The API is deployed before the frontends that depend on a change. |
| A8 | **Documents / PDF**: rendered from HTML templates with headless Chromium (Browsershot or Gotenberg — chosen in the documents sprint), because the invoice must reproduce mockup v6 exactly. |
| A9 | **Integrations** behind interfaces with fakes for development and tests: Stripe (payments, test mode), Microsoft Graph for Exchange (email; Mailpit locally). |
| A10 | **Local ports**: engine 3000 · panel 3001 · API 8000 (· ui playground 3010). |
| A11 | **The panel.** RMS and CRM live in one Nuxt app with a **system switch in the header** (RMS ⇄ CRM) that swaps the sidebar navigation. The current system is derived from the URL (`/rms/…`, `/crm/…`), so deep links and browser history work; switching goes to the last page visited in the other system. Each system is a **local Nuxt layer** (`layers/rms`, `layers/crm`) with its own pages, components and API client (`useRmsApi()` → `/api/rms`, `useCrmApi()` → `/api/crm`). ESLint forbids imports between the two layers; they share only `anakata-ui` and the panel's shell. Cross-system links (deal → booking) are route links only. Access to each system is a permission (`panel.rms`, `panel.crm`, Sprint 1); a user with only one sees no switch. Merging the frontends changes nothing in the ownership rules: the API still enforces that the CRM has no write path to money. |
| A12 | **Laravel 13** (PHP ≥ 8.3). |

## B · Contradictions between the documents — resolved

| # | Contradiction | Resolution |
|---|---|---|
| B1 | The engine prototype (v3) predates the 12 Sep 2026 decisions: cabins 201–208/301, ANATARA naming, no nationality capture, no park-fee choice, no offer badge slot, ES locale switch. | **Engine design stays exactly as the prototype; engine content and rules follow the decisions** (doc 04 "Changes the engine must make"): Suite 01–08 + Owner's Suite, ANAMARA / ANATIVA, nationality + Ecuador residency per guest, PNG/TCT collection choice, offer badge slot, English only, Stripe only. |
| B2 | Pricing differs: the engine adds a departure-offer %, a −5% online-deposit advantage (+ spa access) and stacking promo codes; the RMS pricing engine (doc 02) has none of these and the RMS has no promo codes. | **One pricing engine, in the API.** Order: doc 02 steps 1–6 per cabin (festive blocks all discounts) → then, on the booking total, in this order: departure/booking offers (RMS Offers, type PCT/AMT/VALUE/CREDIT) → online-deposit advantage → promo code. **Promo codes become an RMS Offer with a `code` field** (never publicly listed). The online-deposit advantage is a business rule `online_deposit_discount_pct` (default 5) with the perk text in engine settings. Stacking follows each Offer's `combinable` flag; business rule `max_total_discount_pct` (default: none). Deposit = deposit % of the discounted cabin total. **PENDING CLIENT** (engine SPEC §10 items 1–4). |
| B3 | Reference formats: engine `ANK-R-YYYY-NNNN` / `ANK-B-YYYY-NNNN`, RMS `ANK-YYYY-NNNN` / `ANK-R-YYYY-NNNN`. | RMS formats everywhere: bookings `ANK-YYYY-NNNN`, requests `ANK-R-YYYY-NNNN`. `ANK-B-…` is retired. Payment references `ANK-YYYY-NNNN-D01/B01/R01`. |
| B4 | Retention: docs 01/02/06 say passport data deleted 2 years after the cruise; doc 07 §8 says 7 years. Medical notes: doc 07 says 90 days after disembarkation; doc 01 implies 2 years. | Retention periods are **configuration**, defaulting to the stricter reading: passport data anonymised **2 years** after the cruise; medical/dietary/mobility notes purged **90 days** after disembarkation; consent log and financial documents 7 years. **PENDING CLIENT** (LEG-002). |
| B5 | Doc 07 says both "stages 5–7" and "stages 5–8" are set by the RMS. | Stages **5–7 are system-set and locked** in the CRM. Stage 8 (LOST) can be set by RMS events **or** by a person with a reason. |
| B6 | Engine SPEC: PNG fee "informational, paid at SCY airport", child cutoff 17. | Superseded by FIN-004 + decisions 1, 4, 5: per-guest category by age at departure and nationality, child cutoff **12**, guest chooses who collects. |
| B7 | Engine SPEC: pay-later hold duration open; payment provider open; yacht names open. | Answered by doc 05: request hold 48 business hours near-term / 5 business days long-lead; web checkout hold 20 + 10 min; Stripe; ANAMARA / ANATIVA. |
