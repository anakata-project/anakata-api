# 08 · Development decisions
Decisions taken by the development team at the start of the build. They sit **above** documents 01–07 and the prototypes in the order of authority, because they resolve contradictions between them. Items marked **PENDING CLIENT** are our working assumption until Anakata confirms; they are implemented as configurable values so changing them later is data, not code.

---

## A · Architecture

| # | Decision |
|---|---|
| A1 | **Four repositories**: `anakata-api`, `anakata-ui`, `anakata-panel`, `anakata-engine`. |
| A2 | **One tightly coupled Laravel application** (`anakata-api`). RMS and CRM are two sections of one codebase and one database (A3), not separate modules. Conventional folders: `app/Models`, `app/Actions/<Domain>`, `app/Services/<Domain>`, `app/Enums`, `app/Policies`, `app/Events`, `app/Listeners`, `app/Http/{Controllers,Requests,Resources}/{Rms,Crm,Engine}`, `app/Support`. No `app/Modules`, no contracts between RMS and CRM, no mirrors, no internal sync events. Route prefixes `/api/rms`, `/api/crm`, `/api/engine` exist for permissions (`panel.rms` / `panel.crm`), the public/private split, and the CRM sensitive-data guard. A Pest arch test keeps CRM controllers off money/booking write paths (see `laravel.mdc`). Foreign keys between RMS and CRM tables are allowed. |
| A3 | **One MySQL 8 database** — `anakata` (app) and `anakata_test` (tests) — with a single MySQL user that has grants on both. RMS and CRM are two sections of one codebase sharing this one database; foreign keys between their tables are allowed (e.g. a booking references a CRM contact; a CRM contact converts into an RMS customer). Sensitive data (passport number, medical/dietary/accessibility notes) is protected in code — encrypted at rest with a dedicated key (`SENSITIVE_DATA_KEY`, separate from `APP_KEY`) — and by a CRM response-guard middleware, not by DB-role isolation. |
| A4 | **Events are side effects only.** Laravel events + queued listeners (Redis, Horizon), dispatched after commit (`ShouldDispatchAfterCommit`): emails, Stripe, engine availability push, CRM tasks raised by booking changes. No outbox, no `EventEnvelope`, no internal sync bus. CRM data derived from bookings (pipeline stages 5–7, lifecycle, LTV) is computed from the booking tables directly. External integrations (Stripe, email, the public engine) still follow doc 07's intent. |
| A5 | **Auth**: Laravel Sanctum SPA cookie sessions for RMS and CRM staff (same user table, on the single default connection). **Permissions are a PHP enum (code); roles are a `roles` table (data)** holding a JSON list of enum values, managed by Admins in the RMS; one role per user. No permissions package or permissions table. The finance and director flags are permissions in the enum. The public engine is unauthenticated and rate-limited. The agent portal (later) gets its own guard. |
| A6 | **Frontends**: Nuxt 4 + Nuxt UI v4 + TypeScript. **One staff panel (`anakata-panel`, SPA) contains both the RMS and the CRM**; the engine is SSR for SEO. Both extend the `anakata-ui` layer via the local path `../anakata-ui` for now (A13). |
| A7 | **API contract**: OpenAPI generated by Scramble; the layer generates TypeScript types from it. The API is deployed before the frontends that depend on a change. |
| A8 | **Documents / PDF**: rendered from HTML templates with headless Chromium (Browsershot or Gotenberg — chosen in the documents sprint), because the invoice must reproduce mockup v6 exactly. |
| A9 | **Integrations** behind interfaces with fakes for development and tests: Stripe (payments, test mode), Microsoft Graph for Exchange (email; Mailpit locally). |
| A10 | **Local ports**: engine 3000 · panel 3001 · API 8000 (· ui playground 3010). |
| A11 | **The panel.** RMS and CRM live in one Nuxt app (one codebase) with a **section switch in the header** (RMS ⇄ CRM) that swaps the sidebar navigation. The current section is derived from the URL (`/rms/…`, `/crm/…`), so deep links and browser history work; switching goes to the last page visited in the other section. Pages live in `app/pages/rms` and `app/pages/crm`; components are organised by feature; one `useApi()`. No local Nuxt layers, no import ban, no `useRmsApi` / `useCrmApi`. Cross-section links (deal → booking) are route links only. Access to each section is a permission (`panel.rms`, `panel.crm`, Sprint 1); a user with only one sees no switch. The API still enforces that the CRM has no write path to money. |
| A12 | **Laravel 13** (PHP ≥ 8.3). |
| A13 | **No CI for now.** Git host is undecided (likely not GitHub). Local quality checks remain mandatory. Apps consume `anakata-ui` via the local path `../anakata-ui` until remote consumption is decided with the git host. |

## B · Contradictions between the documents — resolved

| # | Contradiction | Resolution |
|---|---|---|
| B1 | The engine prototype (v3) predates the 12 Sep 2026 decisions: cabins 201–208/301, ANATARA naming, no nationality capture, no park-fee choice, no offer badge slot, ES locale switch. | **Engine design stays exactly as the prototype; engine content and rules follow the decisions** (doc 04 "Changes the engine must make"): Suite 01–08 + Owner's Suite, ANAMARA / ANATIVA, nationality + Ecuador residency per guest, PNG/TCT collection choice, offer badge slot, English only, Stripe only. |
| B2 | Pricing differs: the engine adds a departure-offer %, a −5% online-deposit advantage (+ spa access) and stacking promo codes; the RMS pricing engine (doc 02) has none of these and the RMS has no promo codes. | **One pricing engine, in the API.** Order: doc 02 steps 1–6 per cabin (festive blocks all discounts) → then, on the booking total, in this order: departure/booking offers (RMS Offers, type PCT/AMT/VALUE/CREDIT) → online-deposit advantage → promo code. **Promo codes become an RMS Offer with a `code` field** (never publicly listed). The online-deposit advantage is a business rule `online_deposit_discount_pct` (default 5) with the perk text in engine settings. Stacking follows each Offer's `combinable` flag; business rule `max_total_discount_pct` (default: none). Deposit = deposit % of the discounted cabin total. **PENDING CLIENT** (engine SPEC §10 items 1–4). |
| B3 | Reference formats: engine `ANK-R-YYYY-NNNN` / `ANK-B-YYYY-NNNN`, RMS `ANK-YYYY-NNNN` / `ANK-R-YYYY-NNNN`. | RMS formats everywhere: bookings `ANK-YYYY-NNNN`, requests `ANK-R-YYYY-NNNN`. `ANK-B-…` is retired. Payment references `ANK-YYYY-NNNN-D01/B01/R01`. |
| B4 | Retention: docs 01/02/06 say passport data deleted 2 years after the cruise; doc 07 §8 says 7 years. Medical notes: doc 07 says 90 days after disembarkation; doc 01 implies 2 years. | Retention periods are **configuration**, defaulting to the stricter reading: passport data anonymised **2 years** after the cruise; medical/dietary/mobility notes purged **90 days** after disembarkation; consent log and financial documents 7 years. **PENDING CLIENT** (LEG-002). |
| B5 | Doc 07 says both "stages 5–7" and "stages 5–8" are set by the RMS. | Stages **5–7 are system-set and locked** in the CRM. Stage 8 (LOST) can be set by RMS events **or** by a person with a reason. |
| B6 | Engine SPEC: PNG fee "informational, paid at SCY airport", child cutoff 17. | Superseded by FIN-004 + decisions 1, 4, 5: per-guest category by age at departure and nationality, child cutoff **12**, guest chooses who collects. |
| B7 | Engine SPEC: pay-later hold duration open; payment provider open; yacht names open. | Answered by doc 05: request hold 48 business hours near-term / 5 business days long-lead; web checkout hold 20 + 10 min; Stripe; ANAMARA / ANATIVA. |
| B8 | Doc 07 §10.5: "Passport and medical data must not be reachable from the CRM service account. Enforce at the database role level, not in application code." | **Superseded.** One database / one user is shared by RMS and CRM (A3). Sensitive data is protected by a dedicated-key encrypted cast (`SENSITIVE_DATA_KEY`) and a CRM response-guard middleware plus architecture tests, not by MySQL role grants. |
| B9 | Doc 07 describes RMS, CRM and the engine as separate systems with field-ownership mirrors, an event bus (§4) and an outbox. | **Superseded inside our app.** RMS and CRM are two sections of one Laravel application and one panel (A2, A11). There are no mirrors, no internal sync events, no outbox and no `EventEnvelope`. CRM data derived from bookings is read from the booking tables directly. External integrations (Stripe, email, the public engine) still follow doc 07's intent (single write path, engine consumes what the RMS publishes, at-least-once side effects via queued listeners). |

## D · Sprint 1 decisions (18 Sep 2026)

| # | Decision |
|---|---|
| D1 | **Sign-in**: email and password, plus "forgot password". No two-factor authentication yet (to be revisited before go-live; Sanctum sessions leave room for it). |
| D2 | **Users**: no self-registration. An admin creates a user, who receives an invitation email with a link, valid 7 days, to set a password. The first admin in each environment is created with `php artisan anakata:create-admin`. Users are never deleted, only disabled. |
| D3 | **Roles**: three seeded system roles, Admin, Manager and Sales Exec. System roles cannot be deleted or renamed. **Admin always holds every permission** (including permissions added later) and cannot be edited. Manager and Sales Exec permissions can be edited. Admins can add roles. One role per user: a user who needs a flag their role lacks (the prototype's "CFO (external) · Agent + finance") gets a role that includes it. |
| D4 | **Permissions per area** (`bookings.*`, `requests.*`, `offers.*`…). Refunds are split into `refunds.approve` (director group) and `refunds.execute` (finance group). The own-records rule lives in policies, not in the enum. The one related permission is `records.act_on_any`, which lets a role bypass the rule (Admin by default). |
| D5 | **One append-only `change_history` table** for every entity: when, who, event, before/after, reason where required. Rows are never updated or deleted (enforced in code and by database triggers). **Sensitive values are never written to history**, only the field name. Rates, business rules and engine settings additionally keep their own publish history (doc 02). |
| D1a | **Password length** (19 Sep 2026): minimum **8** characters, no composition rules; `uncompromised()` (breached-password check) in production only. Replaces the 12 characters specified in Sprint 1 task 03. |
| D6 | **Time**: everything is stored and exchanged in UTC (ISO-8601 with `Z`). The panel shows timestamps in Galápagos time (`Pacific/Galapagos`, UTC−6, no daylight saving). Calendar dates (departure dates, date of birth) are dates and are never shifted. The business time zone also decides the year in references (`ANK-2026-…`) and, later, business-hour calculations. |

## E · Sprint 2 decisions (19 Sep 2026)

| # | Decision |
|---|---|
| E1 | **Configuration is versioned documents.** Rates, business rules and engine settings are each an append-only series of published versions, one table per kind (`rate_versions`, `business_rule_versions`, `engine_settings_versions`). A version holds the whole document as JSON, validated by a typed PHP class, and is never changed after it is written. The current value is the highest version. |
| E2 | **No stored drafts.** The draft lives in the editor, as in the prototype. Publishing sends the whole document plus the version the edit started from (`base_version`). If someone else published in between, the API answers 409 and nothing is overwritten. The API can validate a draft and run the price check without storing anything. |
| E3 | **Approval reference**: a mandatory text field for every rates and business-rules publish, and for engine-settings publishes that change a rule field. Copy-only engine-settings changes may leave it empty. No second-person approval step. |
| E4 | **Publishing applies immediately.** No "effective from" date: rates are already chosen by the departure's sailing year, and confirmed bookings keep their contracted price. |
| E5 | **The business-rules registry is code, the values are data** (the same split as permissions and roles). The registry lists every rule with its source code, status, source value and where it is set. The API computes the "differs from source" flag. |
| E6 | **Engine settings have two edit levels**, as in the prototype. Rule fields (guests, calendar, fees, charter response SLA) need `engine_settings.manage` (Admin by default). Copy fields need the new permission `engine_copy.manage` (Admin and Manager by default). |
| E7 | **The core pricing calculation lives in the API** as a pure service (doc 02 steps 1–7). The eight reference prices in doc 02 are its tests. Offers, promo codes and the online-deposit discount are added with the engine API (08 B2). Bookings will store the id of the rates version they were priced with (Sprint 4). |
| E8 | **Items pending with the client are built with their documented defaults and marked pending** in the registry: `online_deposit_discount_pct` 5 and `max_total_discount_pct` none (08 B2, PENDING CLIENT), and the cancellation bands, whose logic is live while the customer-facing text is still being written (LEG-001). |
