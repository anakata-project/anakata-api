# Task 11 · anakata-panel · Panel shell with the RMS ⇄ CRM switch
**Repo:** anakata-panel · **Sprint:** 0 (read `../anakata-api/docs/sprints/sprint-00/README.md` first)
**Needs:** task 06 (API health + CORS) and task 10 (`anakata-ui` v0.1.0).

## Goal
One staff app, running on port **3001** as an SPA (`ssr: false`), that contains both systems:
- A **system switch in the header** (RMS ⇄ CRM) swaps the sidebar navigation.
- The RMS side looks like the RMS prototype's shell; the CRM side looks like the CRM prototype's shell.
- Every navigation item leads to a placeholder page.
- The app reaches the API.

## Do — wire the layer
1. Remove the starter's own CSS content and its `css` entry. Delete the starter's demo pages and components.
2. `@nuxt/ui` and `tailwindcss` at **the same versions as anakata-ui**.
3. `nuxt.config.ts`:
   ```ts
   extends: [
     process.env.ANAKATA_UI_LOCAL
       ? '../anakata-ui'
       : ['github:<org>/anakata-ui#v0.1.0', { install: true, auth: process.env.GITHUB_TOKEN }],
   ],
   modules: ['@nuxt/ui'],
   ssr: false,
   devServer: { port: 3001 },
   runtimeConfig: { public: { apiBase: 'http://localhost:8000' } },
   ```
4. `.env.example` with `ANAKATA_UI_LOCAL=1`, `NUXT_PUBLIC_API_BASE=http://localhost:8000` and `GITHUB_TOKEN=`, each explained in a comment.

## Do — structure (see `panel.mdc`)
5. Create the two local layers, `layers/rms/` and `layers/crm/`, each with:
   - `app/pages/<system>/…`
   - `app/components/<system>/`
   - a system-scoped API composable: `useRmsApi()` wraps the layer's `useApi()` with prefix `/api/rms`, `useCrmApi()` with `/api/crm`
   - `navigation.ts` exporting its sidebar tree (groups → items: label i18n key, glyph, route, sprint number)
6. **System registry** in `app/`: a list of the two systems (id, label, home route, navigation, brand subtitle) and a `useSystem()` composable. It derives the current system **from the route prefix** and remembers the last route per system in `localStorage`.
7. **ESLint `no-restricted-imports`** so `layers/rms/**` cannot import from `layers/crm/**` and vice versa. Add a deliberately failing import in a scratch file, confirm ESLint catches it, then delete the file.

## Do — the shell
8. **Layout**, from the RMS prototype:
   - Left `aside`: 220px, bg `--forest`, 1px `--hair` right border, 24px vertical padding, with the brand block and the current system's navigation.
   - Top bar containing:
     - the page title (prototype h1 style)
     - a slot for the date-range filter
     - **the system switch**
     - a **role switcher placeholder** as in the prototypes (does nothing until Sprint 1)
     - `AnkThemeToggle`
     - the system's primary action where its prototype has one (RMS: **＋ New Reservation**)
9. **The system switch.** A two-option segmented control, `RMS | CRM`. Style it like the prototypes' existing mono segmented or toggle controls (find the closest one and name it in the report); the active option is marked the same way. Selecting the other system navigates to the last page visited there, or its home. It must be reachable by keyboard.
10. **Per-system shell differences.** When the CRM is active, show the CRM prototype's variants of the brand block, subtitle and header controls wherever they differ from the RMS. List every difference in the report.
11. **Navigation**, exactly as each prototype renders it:
    - RMS, expected from doc 01:
      - RESERVATIONS: Booking Requests, Calendar, Yacht Layout, Bookings
      - COMMERCIAL: Payments & Revenue, Rates & Promotions, B2B & Agent Portal, Contacts In
      - OPERATIONS: Holds & Waitlist, Refund Approvals, Internal Blocks, Documents & Manifests, Guest Experience
      - BOOKING ENGINE: Itineraries, Departures, Offers, Engine Settings, Engine Map
      - ADMIN: Permissions, Business Rules
    - CRM: as its prototype renders it. Doc 07 §9 names tabs that must exist: Pipeline & Forecast, Tasks & SLA, Web & Engine Activity, Campaigns & Offers, Consent & Data Rights, Documents & Delivery, System → Sync & Field Ownership.
    - **The prototypes are authoritative.** Report every difference from docs 01 and 07.
    - Hover and active states as in the prototype (`.nav a`: padding 10px 22px, `--iv62`, 13px, 2px left border).
12. **Routes.** One per nav item: `/rms/<group>/<item>` and `/crm/<group>/<item>` (e.g. `/rms/reservations/booking-requests`, `/crm/pipeline`). Each shows an `AnkPanel` empty state with the page title and "Coming in Sprint N". `/` redirects to the RMS home, and `/rms` and `/crm` redirect to their system's home (the page each prototype opens on).
13. **API status.** A small `ApiStatus` indicator in the shell, styled like the prototypes' small mono status text. It calls `GET /api/health` and shows `API · OK` or `API · DOWN`.
14. All navigation labels and shell text go through i18n (`en.json`).
